# PartnerLedger インポート手順書

新しいPower Platform環境へ、PartnerLedgerのマネージドソリューションをインポートして使える状態にする、管理者向けの手順です。上から順に進めれば、利用者がアプリで取引先・担当者・契約・名刺・承認を使える状態になります。

アプリの使い方（利用者・承認者・PartnerLedger管理者の操作）は[説明書](user-manual.md)にまとめています。導入後、利用者へ案内してください。

> この手順書は2026-09-27時点の版です。同日のインポート試験（英語ベースの環境）で分かった点を反映しました。「未確認」と書いた箇所は、次のインポート試験で確かめてから確定します。

## 0. 全体の流れ

| 順番 | 作業 | 担当 |
| --- | --- | --- |
| 1 | 前提条件を確認する | Power Platform管理者 |
| 2 | 承認グループと管理者アカウントを用意する | Microsoft 365管理者、環境管理者 |
| 3 | 接続を作り、ソリューションをインポートする | 環境管理者 |
| 4 | セキュリティロールを割り当てる | 環境管理者 |
| 5 | アプリで初期設定をする（契約種類。承認設定は必要なときだけ） | `PL システム管理` |
| 6 | フローとアプリを確認し、利用者へ共有する | 環境管理者 |
| 7 | 受入シナリオで動作を確かめる | 環境管理者、利用者代表 |

インポート後にプラグインの実行ユーザーを設定したり、承認設定の行をDataverseで作ったりする作業はありません（2026-09-27の版から不要）。

## 1. 前提条件

- **Dataverseのある環境**：PartnerLedgerのデータはDataverseに保存します。
- **Code Appsの有効化**：Power Platform管理センター → 環境 → 設定 → 製品 → 機能 → 「Power Apps code apps」をオンにします（[公式](https://learn.microsoft.com/power-apps/developer/code-apps/overview#enable-code-apps-on-a-power-platform-environment)）。
- **利用者のライセンス**：Code Appsを使う利用者には、Power Apps Premium（または従量課金・App Pass・自動割当）が必要です（[公式](https://learn.microsoft.com/power-apps/developer/code-apps/overview#license-end-users-with-power-apps-premium)）。最新の条件はMicrosoftのライセンスガイドで確認してください。
- **AI Builder**：名刺の読み取りにAI Builderの名刺モデルを使います。環境でAI Builderが使えること、AIクレジットがあることを確認します。
- **承認機能**：Power Automateの承認を使います。環境で最初に承認フローが動くときに、承認用のDataverseテーブルが自動で準備されます。
- **環境の言語**：日本語の環境でも英語の環境でも使えます。アプリの画面は日本語です。英語の環境では、Power Appsの管理画面に出るテーブル名は日本語、一部の列名は英語で表示されます。取消ボタンなどの管理者判定は、ロール名「`PL システム管理`」「システム管理者」「System Administrator」で照合します。日本語・英語以外の言語の環境では、環境のシステム管理者ロールの名前が一致しないため、PartnerLedgerの管理者には必ず`PL システム管理`を割り当ててください。

## 2. 承認グループと管理者アカウントを用意する

### 2-1. 承認グループ（Microsoft 365グループ）

承認者の集まりをMicrosoft 365グループで作ります。承認依頼は、申請が提出されるたびにこのグループのメンバー（2-2のチームに紐づくグループ。ゲストは除く）を読み、**メンバー一人ひとりへ**送られます（版0.1.0.5から）。ゲストはDataverseのチーム（メンバーシップの種類「メンバー」）に入らずアプリで申請を開けないため、承認依頼も送りません。メンバーの誰か1人が承認・却下すると結果が反映され、ほかの人の依頼は閉じます。個人あてなので、対応するOutlookではメールの中で承認・却下でき、Teamsの「承認」アプリにも通知が出ます。

1. Microsoft 365管理センターで、承認者をメンバーにしたMicrosoft 365グループを作ります（既存のグループでも構いません）。
2. グループのメールアドレスを控えます（手順3の環境変数に使います）。
3. **グループの設定を変えます**（Microsoft 365管理センター → チームとグループ → 対象のグループ → 設定）。メンバーを読めなかったとき（接続の失敗など）だけ、承認依頼はグループのアドレスへ送られます。そのときに届くよう、次の2つをオンにしておきます（[公式](https://learn.microsoft.com/power-automate/group-approvals#known-issues-and-limitations)）。
   - 「組織外のユーザーがこのグループにメールを送信できるようにする」（英語表示では「Let people outside the organization email this team」）：承認依頼のメールはMicrosoftの送信サービスから届くため、組織外の差出人として扱われます。オフだとグループにも届きません。オンにすると組織外の誰でもこのグループへメールを送れるようになるため、承認専用のグループを使うことを勧めます。
   - 「グループの会話とイベントのコピーをグループメンバーの受信トレイに送信する」（英語表示では「Send copies of team emails and events to team members' inboxes」）：オフだと、グループのメールボックスに届くだけです。

宛先は**提出した時点のメンバー**で決まります。あとからグループに加わった人は、それより前の依頼には応答できません。グループから外した人も、外す前に届いた依頼には応答できます（最長21日）。承認者を外すときは、進行中の申請を管理者が取り消し、申請者に出し直してもらってください。

メンバーを読めずにグループあてになったときは、メールの中では承認できず、**Teamsの通知も届きません**（Teamsの通知は個人あての承認だけ）。メンバーは承認依頼のメールのリンク、Teamsの「承認」アプリ、Power Automateの承認センターで応答します。グループあてになったときは、運用管理者（2-3、フローのDataverse接続のアカウント）へ「[PartnerLedger] 承認依頼をグループあてに送りました」というメールが届きます。Office 365 Groupsの接続と、グループにゲスト以外のメンバーがいるかを確かめてください。

承認依頼そのものを作れなかったとき（宛先の誰かを承認サービスが見つけられない、など）は、申請を自動で「取消」にして理由を残し、運用管理者へ「[PartnerLedger] 承認依頼を作れませんでした」というメールを送ります。フローの実行は失敗として記録されます。申請者は、原因を直した後に出し直せます。

### 2-2. Dataverseのグループチーム

1. Power Platform管理センター → 対象環境 → 設定 → ユーザー + アクセス許可 → チーム → 「チームの作成」。
2. チームの種類は「Microsoft Entra Office グループ」、グループ名は2-1のグループ、メンバーシップの種類は「メンバー」を選びます（[公式](https://learn.microsoft.com/power-platform/admin/manage-group-teams#create-a-group-team)）。
3. 手順3の環境変数に入れるIDを控えます。次の**どちらでも**構いません。
   - DataverseのチームのID（`teamid`）
   - 2-1のMicrosoft 365グループのID（Entraのオブジェクト ID。Microsoft TeamsのチームIDと同じ値）

   ブラウザで次のURLを開くと、グループに紐づいたチームの一覧で両方を確かめられます（`<環境>`は環境のURL）。

   `https://<環境>/api/data/v9.2/teams?$select=name,teamid,azureactivedirectoryobjectid&$filter=azureactivedirectoryobjectid ne null`

   `teamid`がDataverseのチームID、`azureactivedirectoryobjectid`がグループのIDです。**DataverseのチームIDを入れることを勧めます。** グループのIDのままにしておくと、後で同じグループのチームが別の部署にもできたときに、どれか決められず処理が止まります（その場合はDataverseのチームIDに変えてください）。

### 2-3. 運用管理者アカウント

PartnerLedgerのフロー（承認依頼の送信、21日期限での自動取消、担当者への共有の付け直し、名刺の読み取り、日次通知）の接続に使うアカウントを1つ決めます。プラグイン（Dataverse上のサーバー処理）はこのアカウントに依存しません。

- 有効で、Power Platformのライセンスを持つこと
- 環境の**システム管理者ロールをユーザーへ直接**割り当てること（Team経由ではなく）
- 個人の異動・退職の影響を受けにくい、運用用のアカウントを推奨します

## 3. 接続を作り、ソリューションをインポートする

### 3-1. 接続を用意する

運用管理者アカウントで Power Apps（make.powerapps.com）→ 対象環境 → 接続 を開き、次の接続を作ります。

| 接続 | アカウント | 使いみち |
| --- | --- | --- |
| Microsoft Dataverse | 運用管理者アカウント | 承認フロー、担当者の共有、名刺の読み取り、日次通知 |
| 承認（Approvals） | 運用管理者アカウント | 承認依頼の送信。承認センターの「送信済み」に表示されるのはこのアカウント |
| Office 365 Groups | 運用管理者アカウント | 承認依頼の宛先にする、承認グループのメンバーの読み取り（版0.1.0.5から） |
| Office 365 Outlook | 通知の送信元にしたいメールボックスのアカウント | 契約期限・名刺滞留の日次通知メールと、承認された申請を反映できなかったときの申請者へのメール |

Dataverse接続を運用管理者アカウントで作るのは、次の2つの処理で管理者の権限が要るためです。承認の21日期限での自動取消と、担当者への共有の付け直しです。承認依頼をグループあてに送ったときなどの知らせも、このアカウントのメールアドレスへ届きます。

Office 365 Groupsの接続のアカウントは、承認グループのメンバーを読める必要があります（通常の設定なら、組織の利用者はグループのメンバーを読めます）。読めないと、承認依頼は毎回グループあてになります。

データ損失防止ポリシー（DLP）を使っている環境では、Office 365 GroupsをDataverse・承認・Office 365 Outlookと同じグループ（業務用）に入れてください。別のグループだと、承認のフローが止まることがあります。

### 3-2. インポート

1. Power Apps → ソリューション → インポート で、PartnerLedgerのマネージドソリューション（zip）を選びます。
2. **接続参照**の画面で、4つの接続参照に3-1の接続を割り当てます（[公式](https://learn.microsoft.com/power-apps/maker/data-platform/import-update-export-solutions)）。

| 接続参照 | 割り当てる接続 |
| --- | --- |
| PartnerLedger Dataverse（`pl_dataverse`） | Microsoft Dataverse（運用管理者） |
| PartnerLedger 承認（`pl_approvals`） | 承認（運用管理者） |
| PartnerLedger Office 365 Outlook（`pl_office365outlook`） | Office 365 Outlook（通知の送信元） |
| PartnerLedger Office 365 Groups（`pl_office365groups`） | Office 365 Groups（運用管理者） |

3. **環境変数**の画面で、2つの値を入れます。

| 環境変数 | 値 |
| --- | --- |
| `pl_ApprovalGroupAddress` | 2-1の承認グループのメールアドレス |
| `pl_ApproverTeamId` | 2-2で控えたID（DataverseのチームIDか、グループのID） |

   **入力欄に名前が出ないとき**：2026-09-27、英語だけが有効な環境へ版0.1.0.3をインポートしたとき、この画面の2つの入力欄に名前（表示名・説明）が出ませんでした（環境変数の名前に日本語しか付いていなかったため）。版0.1.0.4からは英語の名前も付けたので、英語の環境でもこの画面に名前と説明が出ます（2026-09-28、同じ環境へ0.1.0.4を新規にインポートして確認）。それでも名前が出ないときは**入れる値の形**で見分けます。
   - `@`を含むメールアドレス → 承認グループ宛先（`pl_ApprovalGroupAddress`）
   - `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`の形のID → 承認者Team ID（`pl_ApproverTeamId`）

   2026-09-27の試験では、上がメールアドレス、下がTeam IDの欄でした（1回の観察です。並び順は保証されていません）。入れ違えると承認の申請がエラーで止まります。インポートした後に、下の「既定のソリューション」の画面で、名前（`pl_ApprovalGroupAddress` / `pl_ApproverTeamId`）と値の組み合わせを確かめ、違っていれば直してください。版0.1.0.3では、インポートした後のこの画面に、英語の環境でも日本語の表示名が出ました（2026-09-27、同じ環境で確認）。

4. インポートを完了します。日本語が有効でない環境では「Translated labels for the following languages could not be imported ... 1041」という警告が出ますが、問題ありません（日本語の翻訳が取り込まれないだけで、アプリは動きます）。

環境変数の値は、インポートした後でも変えられます。Power Apps → ソリューション →「**既定のソリューション**」→ 環境変数 → 対象を開き、「現在の値」を編集します（マネージドソリューションの画面からは編集できません。[公式](https://learn.microsoft.com/power-apps/maker/data-platform/environmentvariables#frequently-asked-questions)）。

### 3-3. 版0.1.0.4から更新するとき

版0.1.0.5では接続参照が1つ増えました（`pl_office365groups`）。すでに0.1.0.4を入れている環境では、次の順で更新します。

1. 3-1のOffice 365 Groupsの接続を作ります。
2. インポートの**前に**、今の状態を控えます。PartnerLedgerのフロー5つがオンかオフか、接続参照（3つ）にどの接続が割り当たっているか、環境変数の2つの値です。
3. 3-2と同じ手順で、新しいzipをインポートします（アップグレード）。接続参照の画面で、`pl_office365groups`にOffice 365 Groupsの接続を割り当てます。接続を割り当てないと、承認のフローがオフになり、承認依頼がすべて止まるおそれがあります。
   アップグレードでも環境変数の画面が出て、今の値（「ターゲット環境の値」）が入った状態で「2 個の更新プログラムが必要」と表示され、「インポート」が押せないことがあります（2026-09-30、0.1.0.4→0.1.0.5で観察）。値は変えずに、各欄の末尾の1文字を消して打ち直し、欄の外をクリックすると押せるようになりました。
4. インポートの**後に**、2で控えた内容と突き合わせます。フロー5つがオンで、接続参照4つに接続が割り当たっていることを確かめます。失敗したインポートが途中まで反映されていないかも、同じく控えと比べます。
5. 申請を1件出して、承認依頼がメンバー一人ひとりへ届く（メールの中で承認できる）ことを確かめます。

> 未確認：DataverseにDynamics 365アプリが入っていない環境で、ソリューションの依存（ユーザー・チーム表のメタデータ）がインポートを止めないか。2026-09-27の試験環境ではインポートが通ったが、その環境にDynamics 365アプリがあったかは確かめていない。

## 4. セキュリティロールを割り当てる

| ロール | 割り当てる相手 | できること |
| --- | --- | --- |
| `PL 利用者` | 利用者全員（ユーザーまたはグループチーム） | 取引先・担当者・契約・名刺の登録と閲覧、変更の申請、自分の下書き・差戻し申請の取下げ。**取引先を登録する人には必ず割り当てます**（`PL システム保守`だけでは、登録時に作られる共有設定を読めません） |
| `PL 承認` | 2-2の承認グループのチーム | 全申請の閲覧（承認はTeams・Outlookの承認依頼から行う） |
| `PL システム管理` | PartnerLedgerの管理者（**ユーザーへ直接**） | 契約種類・承認設定の管理、提出中の申請の理由付き取消、申請者不在の下書きの取消 |
| `PL システム保守` | 運用・保守の担当者 | 保守作業用の広い権限 |

- 利用者には環境の標準ロール「Basic User」も必要です。ユーザー一覧とロール名の読み取りに使います。
- `PL システム管理`はTeam経由だと管理者として判定されず、取消ボタンが表示されません。**必ずユーザーへ直接割り当ててください。**

## 5. アプリで初期設定をする

### 5-1. 承認設定（必要なときだけ）

どの変更を承認対象にするかは、インポートした時点で次の既定値になっています。Dataverseに行を作る作業はありません。

| 変更 | 既定値 |
| --- | --- |
| 会社名の変更 | 承認が必要 |
| 取引状態の変更 | 承認が必要 |
| 住所の変更 | 承認なしで直接変更 |
| 代表電話の変更 | 承認なしで直接変更 |
| 主担当の変更 | 承認が必要 |
| 契約の更新・終了の判断 | 承認が必要 |

変えるときは、`PL システム管理`（またはシステム管理者）を**ユーザーへ直接**持つ人が、アプリの「設定」→「承認が必要な変更」でチェックを変えて「保存する」を押します。保存するたびに新しい版として記録され、過去の版も残ります。保存すると、それまでに出ていた申請に次の影響があります（保存の前に画面にも表示されます）。

- 承認待ちの申請：承認されても反映されず「反映失敗」になります。
- 差戻し中の申請：再提出できなくなります。申請者に取り下げて出し直してもらいます。

### 5-2. 契約種類

`PL システム管理`のユーザーがアプリの「設定」→「契約種類」で、使う契約種類（例：基本取引契約、秘密保持契約）を登録します。契約種類が1つもないと、契約を登録できません。

## 6. フローとアプリを確認し、共有する

### 6-1. フロー

ソリューション内の5つのフローは、インポートすると自動で「オン」になります。オンになっていることを確認します。

| フロー | 動き |
| --- | --- |
| PartnerLedger_ApprovalGroupBridge_v1 | 申請の提出で承認依頼を送り、結果を戻す。承認依頼には申請者・申請内容の概要（変更前→変更後）・アプリで申請を開くリンクが載る。**21日間応答がなければ申請を自動で取り消す**。承認されたのに反映できなかった（反映失敗）ときは申請者へメールする |
| PartnerLedger_ContactCreate_ReapplyParentShare_v2 | 担当者の登録時に、取引先と同じ共有を担当者にも付ける |
| PartnerLedger OCR Business Card - R12-C | 名刺画像をAI Builderで読み取る |
| PartnerLedger_NotificationDaily_v1_QueueStopped | 毎日7:00（日本時間）に通知対象（契約期限・名刺の滞留）を集める |
| PartnerLedger_NotificationDaily_v1_Delivery_v2 | 毎日8:00（日本時間）に通知メールを送る。件名と本文は「解約通知期限が近づいています：契約名」のように業務の言葉で、期限の日付とアプリへのリンク（名刺は確認画面へ直接）が付く |

日次通知はインポートした翌朝から実データを対象に動きます。通知先と送信元を確認し、まだ送りたくない場合は日次通知の2つのフローをオフにしておいてください（詳細は[通知の導入](notification-deployment.md)）。

### 6-2. アプリの共有

Power Apps → アプリ → PartnerLedger → 共有 で、利用者（またはセキュリティグループ）へ共有します。スマホでも同じアプリをブラウザで使えます。承認者（2-1のグループのメンバー）にも共有してください。承認依頼のリンクからアプリを開くためです。

承認依頼のリンクは、承認フローがこの環境のアプリの開くURLを読んで作ります（環境変数の設定は不要）。読めなかったときは、リンクがPower Appsの入口になります（承認依頼そのものは送られます）。

## 7. 受入シナリオ

導入後、次の順に動作を確かめます。一般利用者（`PL 利用者`だけを持つ人）と管理者の2人で行ってください。

1. 利用者：取引先を登録する → 「共有設定」タブに承認グループ（閲覧）と、主担当が登録者と別の人なら主担当（編集）が最初から出ている → 別の人を閲覧で追加できる
2. 利用者：担当者と契約を登録する
3. 利用者：会社名の変更を申請する → Teams・Outlookに承認依頼が届く（申請者・変更前後・リンクが載っている） → リンクでアプリの申請が開く → 承認すると取引先名が変わる
4. 利用者：もう1件申請して下書きのまま「取り下げる」 → 同じ対象で新しく申請できる
5. 管理者：提出中の申請を理由付きで「取り消す」 → 取消になる
6. 管理者：「設定」→「承認が必要な変更」でチェックを1つ変えて保存する → 「保存しました（版1）」と出る。元に戻したいときは、もう一度変えて保存する（版2）
7. 利用者：名刺の画像を1枚選ぶ → 読み取り結果を確認して登録する。続けて、登録済みの取引先と同じ会社の名刺をもう1枚選ぶ → 確認画面で「既存の取引先に担当者として追加」が選ばれ、その取引先の担当者として登録できる
8. 翌朝：日次通知が届くことを確認する（対象があれば）

## 8. 運用のポイント

- **承認依頼が承認センターに残る**：PartnerLedgerで取り消した申請や、21日の期限で自動取消になった申請の承認依頼は、承認センターに残ります。応答しても反映されません。消したいときは、承認の接続のアカウント（運用管理者）が承認センター（Power Automate または Teamsの承認アプリ）の「送信済み」から取り消します。
- **Teamsの承認アプリで依頼が見えない**：右上の環境の切り替えで、PartnerLedgerの環境を選んでください。
- **名刺の読み取りに失敗した**：ホームの処理待ちで「もう一度登録」から画像を選び直すか、「一覧から外す」で片付けます。

## 9. うまく動かないとき

| 症状 | 確認すること |
| --- | --- |
| 以前の版から更新した環境で、プラグインが「ユーザーが無効」などのエラーになる | 以前の版（2026-09-27より前）では、プラグインに実行ユーザーを設定していました。残っていると、そのユーザーの無効化で止まります。リポジトリの`scripts/clear-plugin-run-as.ps1`で確かめて外してください（既定は確認だけ、`-Apply`で外す） |
| 承認依頼が届かない | 環境変数`pl_ApprovalGroupAddress`、承認フローがオンか、承認の接続が有効か。メールだけ届かない場合は、手順2-1の3（グループの「組織外からのメール」と「メンバーの受信トレイへコピー」）。Teamsの通知はグループあてには出ない仕様。承認センターやTeamsの承認アプリに依頼があれば、承認依頼そのものは作られている |
| 承認しても反映されない | 申請が「反映失敗」なら、承認申請の画面に出る理由のとおり（申請した項目が承認待ちの間に変わった／承認設定が変わった／対象が無効になった）。内容を確かめて申請し直す。申請が「提出中」のままなら承認フローの実行履歴を見る。取消済みの申請なら、反映しないのが正しい動き。実行が失敗していれば原因を直し、管理者が取り消して出し直してもらう |
| 反映失敗のメールが届かない | Outlook接続（`pl_office365outlook`）が有効か、申請者のユーザーにメールアドレスがあるか、承認フローの実行履歴で送信の手順が成功しているか |
| 承認依頼のリンクがPower Appsの入口になる | 承認フローの実行履歴で`List_partnerledger_app`が成功しているか（Dataverse接続のアカウントがアプリの行を読めるか）。アプリがこの環境にインポートされているか |
| 承認依頼のリンクから開くと「リンクの申請が見つかりませんでした」と出る | 開いた人が申請を閲覧できるか（承認者は`PL 承認`を持つグループチームのメンバーか）、申請が残っているか |
| 取消ボタンが出ない、承認設定を変更できない | その人に`PL システム管理`（またはシステム管理者）がユーザーへ直接割り当てられているか |
| 21日経っても自動取消されない／フローが失敗する | Dataverse接続（`pl_dataverse`）のアカウントが、システム管理者または`PL システム管理`を直接持つか |
| 申請を提出すると「承認設定」のエラーになる、設定画面が読み込めない | Dataverseで承認設定の行（導入設定・設定版、`pl_settings`）を直接作った・書き換えた場合、有効な行の中身が正しいか。誤った行を「非アクティブ」にすると、残った有効な行のうち最大の版（無ければ既定値）で動きます。非アクティブにした行も版番号は使用済みのままで、次にアプリで保存すると、その次の番号になります |
| 名刺が「読み取り失敗」になる | AI Builderの利用可否とAIクレジット |
