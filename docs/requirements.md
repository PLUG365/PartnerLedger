## 実行主体とSecurity Roleの簡素化方針（2026-09-23、Application Userなし）

対象テナントにPartnerLedger専用のApplication User／サービスプリンシパルを作らなくても、Solutionの移送実行者が割り当てる標準Dataverse・Outlook接続と4つの人向けRoleで導入・運用できることを完成条件とする。画面からの業務要求は常にInitiating Userの権限で評価する。定期Flowや、Shareなどの限定された特権サーバー副作用を移送実行者の接続／Plugin Step実行コンテキストで処理する場合も、サーバーが要求者・対象行・Partner・状態・要求内容を再検証し、要求者の認可を移送者権限で代替してはならない。Application User／サービスプリンシパルは必須にしない。

構成は標準Dataverse CRUD、所有者／Team／標準共有、標準Power Automateを第一候補とする。固定Application User／実行者ID環境変数には依存しない。同期Share Pluginは、業務認可をInitiating User、必要なACL変更を移送実行者のStep実行コンテキストで行う案を検証する。これは移送先ごとのStep実行者設定、最小Privilege、直接Grant／Modify／Revoke APIの迂回防止、監査主体、失効・引継ぎを受入するまで未確定である。開発環境の移行作業と暫定復旧の現在地はHANDOFF（開発記録、非公開）を正とする。ShareSettingを単純な非同期Flowに置換しない。耐久OutboxとPending／Failed／再試行状態を備えた別設計が必要である。技術Role（Access／Approval／OCR）は人へ割り当てず、対象機能の移行・E2E・人間レビューを終えた後にSolutionから除外する候補とする。これは既存クラウドRoleの削除・割当変更を直ちに許可するものではない。

## 製品の目的・構成

特定組織に限定しない独立台帳として、取引先の増加、担当者の変化、契約と確認事項の期限を管理する。初版の利用規模は50人、取引先1万件、担当者3万件、契約1万件。

画面はCode App 1本で、PCもスマホも同じアプリを使う（スマホはブラウザで開く。画面幅に応じて表示を調整する）。2026-09-26のユーザー判断で、Power Apps Mobile内の独立Canvasアプリは廃止した。Dataverse、Power Automate、AI Builder、SharePointを使う。DecisionFlow管理ソリューション・本体リポジトリは一切変更しない。

CRM同期、契約金額・支払、与信・反社チェックの実施、商談、独自承認エンジン、ブラウザのオフライン動作は初版対象外。

## データ基盤方針（決定：2026-09-11）

PartnerLedgerは、Dataverseの**専用カスタムテーブルを正本**として実装する。CRM標準の`account`／`contact`を取引先・担当者の正本には使用しない。Dataverseの標準テーブルは一般的な顧客・連絡先の用途に適する一方、この台帳は独立導入を前提とし、取引状態、名刺ステージング、契約単位の期限、項目別承認、監査、版固定、冪等性を固有ルールとして持つためである。これは公式の「標準テーブルを優先し、適合しない場合にカスタムテーブルを評価する」という方針に照らした本プロジェクト固有の判断である（[テーブルの種類](https://learn.microsoft.com/power-apps/maker/data-platform/types-of-entities)、[Dataverseのメタデータ](https://learn.microsoft.com/power-apps/maker/data-platform/create-edit-metadata)）。

- 専用テーブルはPartnerLedger用Solutionにまとめ、具体的な論理名・publisher prefix・所有形態・権限は段階2の読み取りと設計レビューで確定する。
- 最低限、取引先、担当者、契約、名刺取込バッチ、名刺ステージング、申請／提出版、掲示板投稿、設定マスタを専用テーブルとして設計する。担当者と契約は取引先へのLookupで関連付け、担当者の会社名は自由入力にしない。
- Dataverse標準のユーザー／チーム等は、所有者・判断者・権限主体として利用してよい。DecisionFlowの標準テーブルと本体は変更しない。
- 将来CRM連携が必要になった場合は、専用テーブルを正本とした明示的な連携を別計画で追加する。初版でAccount／Contactとの双方向同期や、CRM側を同時に書き込める経路は作らない。

## データ境界（論理設計）

業務上必要な論理データ：取引先、担当者、契約、名刺取込バッチ、名刺ステージング、取引先変更申請、契約判断申請、提出版、取引先／担当者の掲示板投稿、契約種類マスタ、導入設定、通知履歴。これは物理テーブル数の指定ではなく、R2より後の機能も含む。重複確認依頼と旧設計の申請閲覧付与は初回リリースの必須業務データから外す。会社共有は標準共有を正本候補とし、独自の取引先アクセス付与台帳を新設計の前提にしない。既存テーブル・行は移行判断まで保持する。チェック項目・実施記録は外部システムの管理対象。取引先・担当者をCRM標準の`account`／`contact`で代替する案は採用しない。

追加設計が必要：契約を対象にした申請、提出版、撮影／入力版とサーバー処理結果の分離、取込バッチ・処理順・作業リースを含む処理冪等キー、通知履歴、導入設定、主管チーム。オフライン対象選択は廃止し、論理モデルおよび初回リリースの物理スキーマに含めない。これは論理モデルであり、列名・publisher・既定権限を確定したクラウドスキーマではない。

画面が呼ぶ操作は検索／詳細取得、名刺確認、申請提出、契約判断申請。承認結果反映はサーバー専用。外部から承認済み値や実行者を任意指定させない。PCの実データ境界は公式生成サービスへ接続し、独自HTTP認証を作らない。

### PL-031の改訂範囲（2026-09-14、ユーザー承認）

- 承認された変更は「承認者グループは全申請を、完了後も閲覧できる」。申請単位の一時共有・申請状態に連動した失効を要件から外す。ロール・グループ所属自体を管理する必要は残る。

- 具体的な権限差分・移行・検証は実装計画（開発記録、非公開）で扱う。要件承認とクラウド適用・既存API廃止の承認を区別する。

## 権限ロール（設計方針：2026-09-14）

PartnerLedgerの業務Security Roleは、次の4つへ集約する。技術用の実行Roleを人へ割り当てる設計にはしない。

| ロール | 用途 |
| --- | --- |
| `PL 利用者` | 許可された取引先・担当者・契約・名刺の通常操作と、自分の申請。対象行の所有・標準共有を超えて全件へ拡大しない |
| `PL 承認` | 全申請・提出版の継続Read、DecisionFlowの判断結果を取り込むための承認業務、承認者として許可された会社共有管理。DecisionFlow本体は変更しない |
| `PL システム保守` | 移送後のFlow接続を設定する運用担当者、OCR／通知／再処理／監査の保守担当者。必要なサーバー側処理を標準接続で実行する人向けRole |
| `PL システム管理` | 契約種類、承認対象、導入設定、管理者取消、権限・監査の管理。環境のSystem Administratorとは別 |

旧7ロールの契約担当・名刺処理担当・基本利用者は`PL 利用者`へ、設定管理者は`PL システム管理`へ、運用担当者は`PL システム保守`へ統合する。会社共有は、旧`pl_AccessGrant`のアクセス管理者専用プロファイルを必須にせず、標準共有と対象行のアクセス権を組み合わせる方式を先に評価する。全利用者が全会社を共有できる権限は与えない。既存プロファイル・実装の切替は、直接API・同期処理・Flowを含めて別途検証する。

Security Roleの権限は累積するため、`PL システム保守`は一般利用者へ付与せず、移送・運用を担当する人に限定する。申請の全件Read、個別の判断権限、PL-030の会社共有管理は目的と対象テーブルを分ける。ロールや所属を外した場合も、別ロール・所有・共有が残っていないかを評価する。4ロールの権限名・深度は最新メタデータから解決し、直接APIでの迂回、Flow接続の過剰権限、想定外・不足・重複・深度違いを監査する。Dataverseの既存ロール、DecisionFlowのロール、環境System Administratorはこの4ロールへ置き換えない。
